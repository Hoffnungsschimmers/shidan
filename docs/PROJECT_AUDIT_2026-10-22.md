## 结论

食单已经形成可持续迭代的产品和技术骨架：本地优先、三栏结构、收藏与记录双入口、餐厅—用餐—照片三表、整数分账本、备份旁路、集中主题组件，以及一组有效的纯逻辑回归测试。现阶段没有证据支持换架构、升依赖或继续堆新入口。

**当前最大不足是数据可靠性没有闭环验证，而不只是 UI 不够精致。** 保存期间换封面、明确清除金额后重载、备份复制失败仍替换原数据、导出与导入限额不对称等，都应排在自动备份、删除撤销和大文件重构前。

本轮补齐范围：完整评估资料、迁移测试资源接线与升级路径用例。发现的业务问题作为后续独立修复批次，未在本轮顺手修改。

## 2. 系统地图与正确的维护边界

### 产品路径
- **清单**：待探访/已用餐、店名地址及餐品搜索、排序、按最新评价和近期排除随机选店。
- **足迹**：时间线与统计；自由文本估算和结构化整数分账本分别保留，预算、年度回顾、单店累计已接线。
- **我的**：六个二级分区；备份、同步、预算、外观、随机偏好、存储与日志。设置长任务属于 MAIN 作用域，离开子页仍继续。
- **一次记录 ≤20 秒**是未实测目标，不是已验证指标；熟店、新店、带照片应分别测量。

### 实际数据流
```text
Screen → ViewModel → MealRepository → MealDao / PhotoStore
                       ↑
SettingsViewModel → BackupStore → Repository 读快照与替换
                 → WebDavStore → BackupStore
                 → LedgerCsvStore / BackupStatePreference / 其他偏好
```
备份、CSV、WebDAV 是旁路，不应照旧概览图全部塞进 Repository。跨页维护协调必须覆盖真实入口，而不是只锁某个设置按钮。

### 已有优势必须保留
1. 核心多表修改在 Room 事务内；正式文件先提交、再查封面与照片双重引用后回收。
2. 枚举编码和历史 schema 保留，无 destructive migration；v3/v4 新列默认值一致。
3. 自由文本按 code point 截断；金额以整数分存储；空金额与有效金额分离。
4. 保存/删除/设置长任务 CAS 防重复，设置 MAIN 共享 ViewModel、常驻错误已有实质修复。
5. 图像多数 AsyncImage 调用有父约束；列表有稳定 id；搜索与昂贵统计分层，纯统计显式传日期和时区。
6. WebDAV 凭据从系统 cloud backup 与 device transfer 排除，恢复暂存目录按调用隔离。

## 4. 条件风险：需要受控测试，不作已发生故障宣称

1. **备份不一致快照**：三次独立DAO读取之间可插入新餐厅/记录，打包前又可删除照片。设置忙碌不阻止其他页写入。先事务快照，再保护/暂存所需文件；只加读事务还不够。验收：暂停打包→并发新增/删图→恢复内容与快照一致。
2. **恢复/清空期间跨页写入**：确认时和实际替换时之间新增内容会被覆盖；恢复运行时新开的旧世代表单还可能写到复用ID。先维护态与表单世代失效，勿把九类设置动作全部粗暴全局串行化。
3. **提交后清理错误语义**：事务已提交、引用查询/清理再抛异常，部分分支返回整体Failure，部分向VM抛出。把已提交结果与回收警告分开，故障注入验证isSaving释放和重试不重写。
4. **异步初始化/进程恢复/幂等**：迟到预填可覆盖输入；加载前默认首帧可能被当有效草稿；提交已成功但导航结果未知后重试可重复新增。普通旋转保留VM，不是这些问题的充分复现；需要加载完成标志、草稿版本和窄提交身份方案，分别测试。
5. **日期/时区/性能**：自然日/月/年只随数据库/偏好发射重算；大数据聚合链未明确移到Default；CPU延迟和帧耗时未测。增加低频日期/前台输入，固定规模量测后才决定分页/SQL聚合。
6. **网络与CSV**：PUT未显式fixed-length/chunked streaming；内网HTTP按字符串前缀放行而非严格host/IP；Manifest又未明确放行cleartext。CSV格式转义不等于公式文本安全。需平台/服务器/目标表格软件验证，不能直接说已泄露凭据或已执行公式。
